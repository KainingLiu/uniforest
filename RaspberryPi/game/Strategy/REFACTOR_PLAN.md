## 三层接口与世界状态

建议在现有 Strategy 下逐步替换，避免只在完整 Task 外面增加一层包装。以下目录为拟定结构：

```text
Strategy/
  mission/       world.py、policy.py、checkpoint.py、recovery.py
  flows/         actions.py、collect.py、deliver.py、build.py
  execution/     compiler.py、runtime.py、transitions.py、profiles.py
control/
  trajectory.py  连续底盘轨迹与视觉控制交接
```

1. 策略层：`decide(world) -> objective`。输入比赛时钟、材料区最近观察、载荷上下界、建筑状态、
   对手观察和自身可信状态；输出采集哪个区、多少块、暂存或搭建的目标。起步用规则和候选目标评分，
   对手信息未知时明确保留未知，避免虚构位置。观测附来源、时间及置信度。
2. 动作层：`expand(objective, world) -> action_flow`。生成 Navigate、AcquireCube、GrabCube、
   InspectCargo、UnloadCargo、Build 等动作与分支。保留颜色、区域、目标数量等语义，不下发轮速。
3. 执行层：`compile(action_window, context) -> execution_plan`，再由 `run(plan)` 监督执行。
   小窗口前瞻，查找逐对衔接，组织底盘/机构/相机时间关系；只在候选和已验证约束内优化。

世界状态应把“发生了动作”和“观察到结果”分别记录：抓取已发起、可能已携带、数量确认、
已卸入搭建区、建筑稳定、剩余材料估计、当前路线锚点。历史观察过期后降低置信度。
对手已成功抓住的方块应退出候选；竞争只针对仍可合法获取的材料。
预估耗时、得分收益和争抢价值可用于宏观排序，但需要实测耗时与可靠感知支撑。

## 衔接编译及运行契约

每个动作保留进入段、主体、退出段；衔接替换前一退出段和后一进入段。
已经替换的段不得由普通动作再次执行。动作仍保持模块化，执行层优化它们的重叠关系。

衔接匹配至少包含动作种类、抓取机构版本、取块区/方向、载荷状态、相机姿态、路线入口和固件能力。
匹配失败时先结束机构、减速停车，再检查下一动作的物理前提；前提不满足则重规划或中止，
停车本身无法保证任意两个动作能正确衔接。

每份衔接配置包括：适用条件、进入速度、交出速度/加速度、机构包络、视觉有效条件、最大盲移距离/时间、
决策截止点、确认要求、失败补偿、验证状态及固件版本。禁止把一个泛化默认值覆盖全部场景。

运行时仍要监督实际结果，静态编译无法提前确定目标丢失、对手取走方块或机构故障。
同一时刻一个执行所有者控制底盘；机构和相机姿态分别受资源占用约束。
机构未释放前，下一动作可以移动和观察，但不能再次启动 Grap、开舱或覆盖舵机命令。
取消后撤销整段计划及其回调，迟到事件按 token/启动代次丢弃。

现有底盘阻塞点：orange_search、方块对准、`_grab_with_wall_press`、`_move_linear` 都在结束路径发零轮速，
定距控制还要求低速到位。连续执行需引入共享轨迹控制，显式支持非零入口/出口与视觉控制接管。
独立动作和异常路径仍须停车，不能全局删除 finally 内的停车逻辑。
正常交接以单一执行所有者传递目标速度、测得速度、航向基准和控制状态，避免两个 PID 同时写轮速。
曲线需检查四轮峰值、加速度/加加速度、坡道和载荷包络，以及整车加伸出机构的扫掠空间。

## 当前相机条件下的抓取连续衔接

首选有限盲移与重新观测结合。2026-10-02 用户将预移期望明确为 80 mm；该值不能当固定块间距或准确下一目标位置。
当前橙色使用固定顶面单应标定（vision/opencv/orange_fixed_geometry.py），机械臂运动时外参变化，
该标定得到的车体坐标失效；盲区画面可记录，不能送入精确抓取控制。

```text
抓取前：保存下一候选的观察、当前锚点、可用横移范围
抓取：执行已标定的机构序列
CHASSIS_CLEAR：在允许包络内向下一候选方向加速，机构继续回收
盲移期间：编码器/IMU 估计短距离进度；相机几何定位无效
相机回位并稳定 + 新帧有效：清除旧目标/滤波，重新关联候选
视觉接管：从当前速度继续搜索/对准；可抓条件满足且机构空闲后再抓
```

未到最大盲移距离前预留制动距离。相机回位延迟、图像失效、到达搜索边界或目标被拿走时，
按剩余空间减速并停止/有界重搜；通信、急停、遥测故障直接中止。
盲移最大时间、位移误差和加速度限制独立存在。编码器打滑误差要计入余量。
相机恢复后允许带初速度接管，但上一抓取结果未知时仅提前执行不依赖结果的部分。

定义五个不同事实：

| 事件 | 生产者与含义 |
| --- | --- |
| CHASSIS_CLEAR | 固件指令进度达到经实机验证的让车条件；只准规定方向及速度/加速度范围 |
| CAMERA_POSE_COMMAND_DONE | 固件已发完回观察位命令；舵机无实际角度反馈，不能直接推导相机已稳 |
| CAMERA_READY | 上位机确认姿态适用、稳定窗口及新鲜有效画面；无反馈时属于需标定验证的估计 |
| MECHANISM_DONE | 机构序列完成，可以接受下一次机构动作；独立于视觉准备 |
| GRASP_VERIFIED | 有真实抓取/载荷证据；动作执行结束只代表序列完成 |

新视觉数据需带采集时间、相机姿态代次及标定版本。当前 VisionResult.timestamp 是处理完成时间，
原始帧有采集时刻；普通 reset_filter 只清滤波，数量检查专用重置才丢弃缓存和处理中旧结果。
应把代次失效机制推广到每次机构改变相机姿态，拒绝跨姿态旧帧，并补偿采集到控制时的车体移动。

通用检测训练可增强多视角识别，但普通检测框输出类别/像素位置/置信度，无法单独给出可靠车体坐标。
未来方案需额外组合已知尺寸关键点/PnP或深度、相机内参、动态机械臂外参和时间同步，
同时解决遮挡、模糊、舵机位置不确定、角点对称性和树莓派推理延迟。
完全离开视野的目标只能短时预测并增加不确定度。当前 YOLO 姿态实验缺少深度真值，禁止直接作为抓取测距。
固定相机调整已由用户暂缓，因此当前迭代先不依赖新增相机或训练模型。

参考：[OpenCV PnP](https://docs.opencv.org/4.x/d5/d1f/calib3d_solvePnP.html)、
[Ultralytics 检测输出](https://docs.ultralytics.com/tasks/detect/)。

## 乐观执行、载荷与补偿

允许先移动再确认。若成功概率为 1-p，成功时节省 S，失败时相对保守执行额外损失 C，
持续核验开销为 H，则预期收益为 `(1-p)*S - p*C - H`。p、S、C 要从实际衔接日志估计。
这个比较只用于满足运动和携带限制的候选；不能把掉块、碰撞或违规惩罚简化成普通时间损失。

当前数量检查会停底盘、确认步进空闲，再改变机械臂姿态采样；只有恢复观察姿态可和后续底盘移动重叠。
它不能直接用作“抓完每一块后边走边验”。第一版可保留整批检查，同时将单次结果标为待核验，
后续如引入吸气压力或独立视觉证据再缩短确认延迟。

发起一次可能成功的抓取即预占一个名额，记录携带数量上下界与紫块名额。
未知结果按上界约束下一次抓取，禁止因未知就补抓第 4 个或第 2 个紫块。
未确认放入己方搭建区前，掉落方块仍保留规则携带账目；舱内相机少一个不足以释放该名额。
确认空抓后可以局部返回/重搜/换目标；“回去”需要锚点和重新观测，对手可能已经取走原目标。
补偿具备次数和耗时预算，结束后重新交给宏观决策。

## 固件冻结与复位

当前 ACTION_CHASSIS_READY=6 是状态值，Grap1/2/3 在完整抬升后发布，Build 在第三块释放后发布。
动作 ID 仍为 1/2/3/4，现有 test_mode=1 仅表示测试等待，不能复用为动作变体编号。
本轮已扩展 Grap1/Grap3 并推迟 Grap2 至完整抬升；上位机默认等待抓取 DONE，验证后再接受提前放行。
后续按实测需要增加少量预置动作变体。
多个里程碑适合带 token 的保持位；若扩展状态载荷，必须独立同步 schema、双方编解码、能力版本与测试。
比赛上位机只选择赛前已烧录并验证的能力；能力缺失时停步串接或拒绝运行所需流程。

急停恢复从语义检查点重新规划。保存已确认的运输/搭建成果、最近观察、比赛标识和计时，
同时标记中断中的动作/载荷/机构状态为未知。禁止从旧 Python 调用位置或固件 stage 直接续跑。
持久化需原子写入并有版本；掉电窗口内的动作结果无法凭日志推断，重启必须核验。
跨进程重启的比赛剩余时间不能直接沿用旧进程 monotonic 值。

规则手册 3.2.1、3.2.3：最多携带 3 块且最多 1 紫；放入己方搭建区才减携带数；
PDF 描述异常处理搬回启动区，完全到达后等待 6 s，携带块归还相应初始位置，比赛时钟持续。
队伍本轮确认的操作约定为携带块就近放回、已有建筑不变、机器人回启动区重新启动；
两种归还位置表述分开记录，待后续策略设计按现场确认规则处理，不自动恢复原槽库存。
恢复流程需要区分本地可恢复的感知失败与正式异常处理；后者需记录真实摆回和重新启动事件，
不从急停时刻开始计算 6 s，也不因串口恢复自动启动。
规则 3.2.2 要求脱离接触后建筑稳定至少 3 s 才计分；Build DONE 不等于已得分。
最优三座建筑及紫顶加成需由后续计分模型按规则实现。

停止与复位状态：

1. `Motor3508_StopAll()` 本轮已在中断保护内清除目标轮速并重置 PID，主机测试覆盖后续 50 次速度环。
   配套固件仍需 ARM 构建、CLion 烧录和实机故障注入验证。
2. `Stepper_Stop()` 清整个轴上下文，累计 pos 也清零。遥测 0 表示软件计数值，不能证明机构已物理归零。
   恢复前需采用已确认的人工复位或硬件归零途径，当前位置未知时禁止自动退回或重放动作。

## 实施顺序与验收

1. 完成 agent 移除；固定当前任务、路线及并行调用的回归基线。
2. 从真实 Task 提取功能动作及结构化结果，让 PlanA/PlanB 由动作流执行；迁移时保持路线和已确认等待。
3. 引入单一底盘执行所有者、相机有效性代次、动作 token 和有界衔接运行时。
4. 独立同步新增固件里程碑/能力契约，并完成停止路径验证；冻结一个可回退版本。
5. 优先实测 Grap3→下一橙块、Grap1→下一橙块、末次抓取→离场；分别登记，禁止默认全局启用。
6. 在这些实际流上完善世界状态、剩余时间与材料估计，再加入有感知依据的对手策略和恢复规划。
7. 最后升级 Navigate 内部曲线；沿用已经确认的功能动作接口与停止语义。
