# Uniforest YOLO 方块识别实施方案

更新日期：2026-09-24。本文合并任务定义、训练目标、损失、数据集、模型选型和接入方案，是 `yolo/` 的统一实施方案。

状态：方案已确认；已实现复用 Robot 摄像头的自动图片采集、任务阶段记录和本地 SQLite 索引，详见 [采集操作说明](DATA_COLLECTION.md)。尚未完成数据标注、模型训练、分割推理或 hybrid 接入；以下训练、测量适配和部署流程仍为待实现内容。自动抽样不替代完整视频评估和毫米定位真值采集。

## 1. 已确定的技术路线

| 项目 | 决定 |
|---|---|
| 模型 | YOLO11n-seg，nano 规模的实例分割模型 |
| 初始化 | 官方通用预训练权重 `yolo11n-seg.pt`，使用方块数据微调 |
| 类别 | `0: orange_cube`、`1: purple_cube` |
| 输出 | 每个方块的类别、置信度、检测框和独立掩膜（mask） |
| 输入 | 先使用 320×320，保持宽高比缩放并补边；必要时对照测试 416×416 |
| 相邻方块 | 由模型直接输出独立实例，不依赖 OpenCV 黑色接缝分割 |
| 损失 | 使用框架标准实例分割损失，包含检测和掩膜监督 |
| 训练 | 预训练微调，先短期冻结主干，再解冻整体微调；使用验证集早停 |
| 优化器 | 首轮使用框架默认/自动选择，并记录实际优化器和参数 |
| 数据增强 | 以真实光照、轻微视角变化和遮挡为主，保持颜色类别语义 |
| 数据划分 | 按完整视频、拍摄批次或场景分组，隔离训练、验证和测试 |
| 部署 | 先验证 ONNX Runtime；性能不足时评估 NCNN |
| 接入 | hybrid：YOLO 识别和分开实例，OpenCV 几何测量，策略层控制 |

YOLO11 官方包含上述分割权重；实例分割输出每个对象的掩膜、框、类别和置信度。[YOLO11 模型说明](https://docs.ultralytics.com/models/yolo11/)、[实例分割说明](https://docs.ultralytics.com/tasks/segment/)

## 2. 任务定义与训练目标

目标是在一套模型中学习通用橙色、紫色方块识别能力，覆盖槽位、相邻排列和建筑堆叠。Task1、Task2、槽位和建筑不分别训练专用类别；建筑中的方块仍按颜色分别识别。

### 2.1 场景范围

| 场景 | 需要识别的内容 | 任务层使用方式 |
|---|---|---|
| Task1 橙色搜索与抓取 | 单个/多个橙色方块，搜索进出画面、近距离对准 | 选择目标、跟踪、横向对准后抓取 |
| Task2 紫色搜索与抓取 | 紫色方块、槽位遮挡、阴影和运动中的方块 | 按紫色筛选目标并完成对准 |
| 相邻方块 | 两块或多块紧贴的方块、细缝、弱边界和部分遮挡 | 保持各方块独立，避免对准整簇中心 |
| 槽位中的半截方块 | 下半部被挡住、仅可见顶部/正面/侧面的方块 | 检测可见实例，另行判断能否可靠测量抓取点 |
| 堆叠建筑 | 多层橙色及橙紫混合建筑中的可辨认方块 | 聚合方块排列与外轮廓，提取建筑定位参考 |
| 空场景与干扰 | 地面、槽位、标线、机械结构、反光及相近颜色物体 | 减少误检和错误锁定 |

每种颜色应尽量覆盖各种排列和遮挡状态。场景通过元数据记录，不变成模型类别。第一版不设 `orange_building`、`slot_orange`、`task1_orange` 等类别。

### 2.2 模型应达到的能力

- 正确区分橙色和紫色方块。
- 对每个可辨认方块输出独立实例，重点解决相邻方块合并问题。
- 对半遮挡、不同视角和建筑堆叠保持一致的类别语义。
- 在距离、曝光、阴影和运动状态变化时保持可用的轮廓定位。
- 抑制背景误检，为目标锁定和几何测量提供依据。

实例分割不要求一定存在黑缝，但仍依赖图像中的可辨认线索和可靠标签。完全不可见的方块不要求推断；边界无法辨认时不能保证正确分开，也不能凭空补出可用于抓取的坐标。

### 2.3 范围边界

`cube` 摄像头承担方块与建筑视觉任务。`tag` 摄像头继续使用 AprilTag/ArUco 与 PnP，不加入 YOLO 类别。

识别含紫色方块的建筑属于模型数据覆盖范围；“识别第一座已建建筑，并以它定位第二座”的相对定位策略在当前代码中尚未实现，需要另行实现建筑关联和几何关系，不能因模型能识别方块就视为已完成。

## 3. 模型输出与标注语义

### 3.1 按物理方块区分实例

每个可辨认的物理方块标注一个实例，提供颜色类别及可见区域的多边形/掩膜。检测框由该实例掩膜的外接范围生成，不只标矩形框。

- 半截方块只标实际可见部分，不补全挡板后面的区域。
- 同一方块的顶部、正面和侧面属于同一个实例。
- 紧贴的同色方块仍标成多个独立实例，不能把整簇合成一个。
- 建筑逐块标注，橙紫混合时保持各块颜色和身份。
- 不将槽位、缝隙、背景或遮挡物像素划入方块掩膜。
- 完全不可见的方块不标注；确实没有目标的图片使用空标签。
- 局部边界无法判断的样本进入复核池，不随意拆分，也不把漏标目标当背景加入训练。

如果同一实例的可见区域不连通，原始标注需保留同一实例身份；导出前验证训练格式能否正确表示。不能为了拼成单一多边形而错误填满遮挡区域。

### 3.2 输出与测量的区别

模型只保证表达可见区域的预测。半截方块的掩膜中心不一定是物理方块中心；投影宽度也不一定等于完整的 100 mm 边长。几何层必须根据有效边缘、已知平面和任务标定确定测量依据，依据不足时不给出有效抓取坐标。

## 4. 训练损失

采用 YOLO11 实例分割的标准损失。核心监督项概念上表示为：

```text
L = λbox · Lbox + λcls · Lcls + λdfl · Ldfl + λmask · Lmask
```

| 项 | 作用 |
|---|---|
| Lbox | 约束每个实例的预测框位置、尺度和重叠程度 |
| Lcls | 学习橙色、紫色分类，配合训练框架抑制背景误检 |
| Ldfl | 按框架实现细化边界框坐标分布 |
| Lmask | 对每个匹配实例的可见区域进行像素级监督 |

以上是监督职责表达，不要求把四个 λ 都实现为独立配置项。确切损失项、权重与归一化方式以锁定版本的实现为准；若框架含辅助项，同样保留并记录。掩膜损失的实现可查官方源码参考。[Ultralytics 损失实现](https://docs.ultralytics.com/reference/utils/loss/)

第一版保留标准损失，不另加颜色空间、建筑、距离、姿态或手工接缝损失。掩膜监督必须落实到逐实例标签；仅增加损失项不能弥补漏标、错误合并或不可见边界。

标准单帧损失不直接保证视频稳定性，位置抖动和目标切换需要在视频评估及跟踪层单独验证。

## 5. 数据集构造

### 5.1 来源与覆盖

主要使用实际 `cube` 摄像头拍摄的图片和视频，保留原始分辨率。320×320 是模型处理尺寸，不是原始数据保存尺寸。

记录拍摄批次、视频、场景、曝光/增益、摄像头安装状态和可获得的距离参考。采集距离、左右位置、轻微倾斜、运动模糊、阴影、反光、磨损和颜色混合排列。

初始抽样配额沿用已讨论比例；按图片主场景归类计数，同时允许记录多个辅助场景标签：

| 主场景 | 初始占比 | 重点 |
|---|---:|---|
| 普通单方块 | 40% | 基础实例与颜色识别 |
| 半截/槽位遮挡 | 20% | 部分可见和结构干扰 |
| 相邻方块 | 20% | 独立实例和共享边界 |
| 堆叠建筑 | 15% | 多层、混色与遮挡 |
| 纯负样本 | 5% | 背景、反光和机械结构 |

比例是起点，不是配额上限。相邻方块是核心难点，根据验证结果优先补充该场景。另统计每类实例数量和遮挡分布，避免图片比例掩盖颜色或目标数量失衡。数据规模由覆盖和学习曲线决定，不把“几百张/几千张”作为效果保证。

### 5.2 划分与质量控制

先按视频、拍摄批次和近重复图像组划分训练/验证/测试，再做数据增强。可先按约 70%/20%/10% 分配，优先保证场景独立性和各类覆盖，而非精确比例。

训练集更新权重；验证集用于模型选择、超参数和阈值调整；独立测试集在方案冻结后评估，不反复用于调参。同一视频的相邻帧及其增强副本不得跨集合。

人工检查整张图片，既修正已有标签，也补全漏掉的可辨认实例。相邻和建筑场景不能只检查自动找到的目标。

### 5.3 伪标签与困难样本

OpenCV 仅作可选标注助手，不作为分割真值。当前橙色算法每簇只定位左首方块，不能自动为整簇所有方块生成正确实例标注。困难场景必须人工补标和修正。

从实际运行中收集漏检、误检、实例合并、重复分割和颜色错误样本，经复核后加入后续训练集，并混入已有普通样本防止遗忘。保留独立测试集，不将它的失败帧回灌同一轮训练。

## 6. 模型选型与训练优化

### 6.1 初始模型与输入

使用官方 `yolo11n-seg.pt`，加载预训练的通用视觉特征，再适配两个类别。首轮不从随机参数训练，也不依赖来源不明的方块专用权重。

以 320×320 作为起点，使用保持比例的 letterbox。640×480 原图对应内容缩放至 320×240、上下补边；标注和输出需按相同几何变换处理。实际图像尺寸以采集结果为准。

若小方块或相邻边界信息不足，进行 416×416 对照实验，并同时记录准确性和树莓派耗时。掩膜分支内部还可能使用更低分辨率特征，不能把输入尺寸直接视为最终边缘精度保证。

### 6.2 优化策略

1. 在小批人工审核数据上完成训练、分割结果和导出流程检查。
2. 短期冻结主干，训练检测/分割头适应方块类别。
3. 解冻整体网络，以较小学习率微调，保持标准损失权重。
4. 依据验证集选择最优权重和早停，重点观察相邻实例分离与半截方块表现。
5. 加入复核后的困难训练样本继续微调，同时保留普通场景覆盖。

首轮使用框架默认/自动优化器，并保存实际选中的优化器、学习率、调度、批量大小、冻结范围、随机种子和最佳轮次。具体轮数、早停耐心值和显存批量大小在训练环境基准后确定，不把对话中的估算直接当作固定最优参数。

训练与推理环境分开管理，锁定 PyTorch、Ultralytics、导出工具和运行时版本；当前 `requirements.txt` 只是依赖草案。保存权重来源、数据版本、划分清单和配置，确保可复现。训练在具备合适 GPU 的电脑上进行，树莓派负责推理验证。

### 6.3 数据增强

增强范围覆盖亮度、温和色温变化、轻微模糊、缩放、裁剪、小角度旋转和符合真实遮挡的变化。所有空间变换必须同步更新实例掩膜。

颜色就是类别依据，禁用会把橙色变成紫色等强色相扰动。限制不符合安装视角的强透视和大旋转。裁剪/遮挡增强后，掩膜必须表示剩余可见区域；不把遮挡物像素保留为目标真值。

首轮不额外堆叠复杂增强。检查框架默认的 Mosaic、MixUp 等是否造成不真实的颜色、边界或尺度，再决定启用强度。

## 7. hybrid 模式与现有代码接入

### 7.1 职责划分

```text
cube 图像
  → YOLO11n-seg：输出各方块的独立 mask、框、类别、置信度
  → 坐标还原：撤销缩放/补边/ROI 偏移，回到原图坐标
  → OpenCV/几何适配：提取有效轮廓、边缘和测量参考，计算坐标
  → 策略层：目标选择、跨帧跟踪、建筑聚合、确认、PID 和动作
```

hybrid 的核心是“学习感知 + 几何测量”。相邻方块由 YOLO 分开；OpenCV 不重新用 HSV 或黑缝决定实例数量，否则会把原有难点带回主流程。

### 7.2 当前几何实现的适配边界

| 场景 | 现有实现依据 | 接入时需要验证 |
|---|---|---|
| Task1/Task2 橙色拾取 | `orange_cluster.py` 提取簇左首方块，`orange_fixed_geometry.py` 使用各任务固定平面映射 | 从每个 mask 提取该平面上的对应边缘/参考点，不能把任意可见面中心直接套入平面映射 |
| 紫色拾取 | `cube_detector.py` 中的四边形、已知尺寸和相机模型 | 可见宽度/边缘是否仍代表完整物理尺度，遮挡时能否可靠测量 |
| 建筑 | `task2.py` 筛选橙色整体轮廓，使用顶部参考边缘与标定公式计算 X/Z | 先将实例聚合到正确建筑，再获得对应顶部参考；混色或层数变化必须复核标定 |

当前建筑代码只接受橙色候选，不能直接消费“多块橙色/紫色实例”。需要新增建筑聚合适配，并防止把相邻两座建筑合成一座。三层建筑的顶边标定不能直接套用到高度不同的六层建筑。

模型不直接回归毫米距离，掩膜也不直接证明定位准确。只有测量依据有效的候选才生成可供控制使用的位置。

### 7.3 接口与模式

计划支持 `opencv`、`yolo`、`hybrid` 模式。`yolo` 模式用于单独查看分割结果和耗时；完成验证后使用 `hybrid` 接入策略。现阶段默认仍使用现有 OpenCV 实现。

适配目标是保留 `CubeDetector` 的生命周期、profile 切换和 `VisionResult`/`BlockInfo` 的控制接口；另保存实例 mask 和诊断数据。需要处理以下接口差异：

- 新模型置信度通常为 0～1，当前接口采用 0～100，部分橙色结果还是固定 80；明确转换，重新验证阈值，不能等同为实际正确率。
- profile 控制允许类别、ROI 和几何标定，不改变模型类别。建筑 profile 必须允许两种颜色进入聚合。
- 输出记录采集/读取、推理完成和结果发布时刻；过期判断考虑图像年龄，不能只以推理完成时间制造“新帧”。
- profile 切换、目标身份变更或后端切换时清除旧跟踪/滤波状态。
- 仓库目录和现有导入统一使用小写 `vision`；集成时验证 Linux 大小写、导入和配置路径，不以 Windows 导入结果代替 Linux 验证。

OpenCV 回退是受条件控制的补充：仅在已验证场景、目标身份和几何检查通过时使用。相邻方块无法分开时，不能把传统整簇结果自动当作可靠单块；无可靠目标时按策略停车并重新确认。保留手动切回 OpenCV 的入口供排障。

STM32 继续接收既有运动/执行器命令，视觉推理和位置解释位于树莓派上。按此方案接入无需改变 UART 协议。

## 8. 部署与实时性

先导出 ONNX 并使用 ONNX Runtime 测试，验证类别、框、掩膜解码及坐标还原与 PyTorch 结果的一致性；核对导出是否包含 NMS，避免漏做或重复处理。速度不足再评估 NCNN，转换后重新验证掩膜和测量精度。

采用采集与推理解耦、仅处理最新帧的方式，避免排队产生越来越旧的结果。一次只对一帧推理，控制线程读取带时间信息的最新结果。

树莓派目标约为 10～15 次有效视觉更新/秒，属于待实测目标。分别记录采集频率、预处理、推理、掩膜后处理、几何计算及整条流程的平均/P95 耗时，并在 AprilTag 等实际并发负载下测试。

此前只查询过 `/dev/video0` 的 15 FPS 能力，未据此证明 `cube` 摄像头或当前算法的真实更新率。实施时按稳定 `cube` 角色核实摄像头能力并测量实际新帧率。15 Hz 吞吐量约对应 66.7 ms 间隔，但不等于相同的端到端延迟，也不保证掩膜分割达到该速度。

## 9. 评估与实施步骤

### 9.1 评估内容

使用独立人工标注视频/图片，按颜色和场景分组报告：

- 框与掩膜的 precision、recall、mAP；固定并记录评估阈值。
- 相邻方块成组全部正确分开的比例，及实例合并、过度拆分、重复预测情况。
- 半截方块漏检率、建筑中可见方块召回率和颜色混淆。
- 空场景误检次数，以及视频中的丢失持续时间和目标误切换。
- 掩膜边缘/控制参考点的误差、静止抖动和有实测真值的毫米坐标误差。
- 整条视觉链的更新率、图像年龄、延迟、内存和持续运行稳定性。

普通场景召回率 95% 可作为首轮观察目标，不代表相邻实例分离或抓取已经达标。相邻场景是首要验收重点；最终阈值结合独立测试和机械允许误差确定，不仅凭总体 mAP 放行。

### 9.2 实施顺序与产物

| 阶段 | 产物 | 进入下一阶段的条件 |
|---|---|---|
| 环境与基准 | 相机角色/新帧率记录、依赖版本、预训练分割推理/导出基准 | 分割链可运行，耗时测量可复现 |
| 数据与标注 | 分组数据、逐实例 mask、人工审核与隔离清单 | 相邻/遮挡/建筑实例语义一致，避免漏标和泄漏 |
| 首轮训练 | 两类分割权重、配置和场景评估报告 | 能分开关键相邻实例，颜色和半截场景可用 |
| 困难样本迭代 | 复核样本、改进权重和对照结果 | 困难场景改善且普通场景不明显退化 |
| 几何适配 | 原图 mask、方块坐标、建筑聚合与定位验证 | 原始标定使用条件成立，坐标误差可接受 |
| 部署与影子运行 | 导出模型、树莓派报告、与 OpenCV 的同帧对照 | 无旧帧积压，实际负载下速度和误差满足控制要求 |
| hybrid 联调 | 策略接入、目标锁定/丢失/切换验证、场地记录 | 相邻抓取及建筑场景实测通过后再切换默认模式 |

训练硬件、锁定软件版本、具体学习率/轮数/批量大小以及最终置信度和验收阈值由基准确定。这些是后续实验参数，不改变已确认的两类统一实例分割方案。

## 10. 目录规划

`yolo` 是 Uniforest 仓库内的子目录，没有独立 Git 仓库。训练数据、大模型和运行产物与源代码分别管理。

```text
RaspberryPi/vision/yolo/
  README.md                   # 仅指向本方案
  docs/IMPLEMENTATION_PLAN.md  # 本文
  requirements.txt            # 当前为草案，实施时区分训练和推理依赖
  collection_config.json      # 已实现：自动采集参数
  collector.py                # 已实现：限流、后台 JPEG 保存、SQLite 索引
  src/                        # 待实现：推理、坐标还原和几何/策略适配
  scripts/                    # 待实现：标注转换、训练、评估、导出
  data/collection/             # 自动采集产物，忽略 Git；命令入口为 tools/collect_cube_data.py
  data/                       # 实例标注与训练/验证/测试分组清单待建立
  models/                     # 待建立：权重、导出模型及其元数据
  reports/                    # 待建立：场景评估和设备性能报告
```
